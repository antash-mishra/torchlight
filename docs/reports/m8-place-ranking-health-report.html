Among your top 10 file results for 50 everyday searches, files from SDKs, module caches and downloaded tools fell from 315 to 192 of 500, and files from your own folders rose from 143 to 225. 3Red flags and things to know

Anything out of range, anything found and fixed while validating, and the trade-offs that come with the change, each explained in plain words.

Red flagA full check reads 1,001 to 1,018 ms (limit 1,000 ms), on both builds

What we saw. The median of five forced full checks was 1,001 and 1,018 ms for M8, and 1,307 and 1,048 ms for HEAD, in the same hour. The M7 Phase 3 report measured 943 to 969 ms on a quieter machine.

Why. M8 does not change scanning: excluding folders adds one comparison per folder against the excluded list, which is empty in this run. Both builds slowed together with the machine's load. What it means for you: nothing new; the full check stays at its limit, as Phase 3 already flagged.

Red flagMemory after a rebuild reads +10.7% (limit +10%), as on HEAD (+10.1%)

This is the open item the M7 Phase 3 report described: everyday memory fell more than memory after a rebuild. M8 adds 2 bytes per entry (0.4 MB at 213k) to every engine, steady and rebuilt alike; the single runs differ by 1 MB, within noise.

WatchTyping at 500k is close to 5 ms on a busy machine

The median of six mirrored runs is 4.77 ms for M8 and 4.75 ms for HEAD (load average 3.5 to 5.3). A first version stored the penalty per folder; every scored entry then needed a second scattered memory read, and p95 rose to 4.91 ms. Storing it per entry (2 bytes, 1 MB at 500k) removed the difference. The 213k real mirror is at 2.8 ms on both builds.

WatchDeep files in your own projects rank a little lower

For model, two files seven folders deep (AndroidStudioProjects/…/app/src/main/cpp/include/model.h) dropped out of the top 10 behind shallower matches of the same strength. That is the rule working as designed; opening such a file adds a personal boost that lifts it again.

WatchKnown-item recall@1 on the real mirror drops by 0.029

This benchmark picks random files as targets. On your home folder 84% of files are in the Android SDK and the Go module cache, exactly the files M8 ranks later, so their first-place hits drop (0.492 to 0.463). recall@10 holds (0.632 to 0.634), and on synthetic corpora recall@10 rises.

Good to knowExact names inside SDKs still come first

For readme, doc, util, build or license, files with exactly that name inside third-party trees still lead: a place penalty never moves a result below a weaker kind of match, and an exact name is the strongest. exclude is the remedy: with ~/Android/Sdk and ~/go/pkg/mod excluded, 311 of the 500 results come from your own folders.

Good to knowA changed exclude list takes effect when the daemon restarts

As with root and allow, the daemon reads its configuration at start-up: run systemctl --user restart torchlightd after editing. The start-up check then removes the excluded folders' saved entries.

Good to knowA folder named sdk counts as installed software

That catches ~/Android/Sdk, the largest source of noise here, but also a project's own sdk folder, whose files then rank a little lower.

ResolvedFound by a test: the crawler kept a stale pointer on bad input

crawl_create promised to set its output to NULL on every invalid call but returned early without doing so when a list was NULL with a nonzero count. The new crawl test caught it; it is fixed.

WatchOne mutation check survives: the score floor of 1

Eleven of twelve deliberately broken rules made a test fail. The twelfth removes the rule that an ordinary result scores at least 1 after its penalty. No real match is that weak today: letters scattered through a folder name or across a path score about 270 or more, above the 256 cap, so the floor is a guard for future scorers and cannot be reached by a test.

Good to knowFound while testing: deltas take trigram statistics from their base

A small update index decides which three-letter pieces are common using the main index only, so a few weak trigram matches can differ from a full rebuild until the next compaction. This predates M8 and does not depend on place ranking; it is recorded in ADR 0047.

Good to knowYour live service runs the first M8 build

It was restarted on the build with per-folder penalties, before the per-entry change. Its ranking is identical; only the extra memory read per result remains until the next rebuild from the m8-place-ranking branch.

4Definitions

Place penalty
A few points (0 to 256) a file result loses for where it lives: 24 per folder beyond three below the indexed folder, plus 128 inside installed or vendored software.
Dependency tree
A folder of software a tool installed or copied in: node_modules, site-packages, vendor, third_party, sysroot, an SDK, a Go module cache, or a version folder such as 27.0.12077973.
Tier (kind of match)
Exact path, exact name, name start, word start, initials, typo, folder name, letters in order, three-letter pieces. A penalty only reorders results inside a tier.
Excluded folder
A folder named with exclude = in the configuration: never read, never watched.
Third-party / own result
Labels for this report only: a result inside SDKs, module caches, downloaded tools or package folders, or inside your workspace and personal folders.
Known-item recall
How often a benchmark query finds its one target file within the first 1 or 10 results.
nDCG@10
A relevance score from 0 to 1 that rewards useful results near the top of the first ten.
Brute-force comparison
Ranking every match the slow, obvious way and checking that the fast engine returns exactly the same list.
Mutation check
Deliberately breaking a rule to confirm the test that guards it fails.
p50 / p95
Percentiles: p50 is the typical case, p95 the slow 5%.
Mirrored order
Running builds A, B, C, C, B, A so that a machine slowly getting busier affects all builds alike.
-O3 / -O0 build
Optimized (benchmark) versus unoptimized debug build. Your live service runs the debug build.

5How this was measured

Ranking panels load each build's engine library (make build/quality_engine.so) and index the same path list; tests/quality/place_eval.py runs the queries and labels results by path. Speed panels use make bench and tests/bench/bench_scenarios.py with optimized builds of HEAD (from a worktree) and M8, alternating.

Details and raw data
  • Live catalog: a read-only SQLite dump of files joined with roots; only aggregate counts are committed (tests/quality/results/2026-10-12-m8-place-live-summary.json).
  • Mixed fixture: tests/quality/evaluate.py against the frozen baseline 7ace90f (its gate) and against HEAD (2026-10-12-m8-mixed-summary.json).
  • make bench: 50k ×3, 500k ×3 and the 213k real mirror ×2 per build, then 18 typing-only runs at 500k in mirrored order for HEAD, M8 with per-folder penalties and M8 with per-entry penalties (tests/bench/results/2026-10-12-m8-lexical.txt).
  • Scenarios: cold, warm, queries, rescan and events phases on the 213k mirror, then warm, queries and rescan again in the opposite order (2026-10-12-m8-213k-*.jsonl).
  • Exclusions: torchlight index on the mirror into fresh databases (2026-10-12-m8-exclude.json).
  • Mutation checks: each rule broken in a copy of the sources, built with the place, place-ranking and crawl tests.
