01 /

Two different kinds of saving.

Disk space is how much storage Torchlight occupies. RAM is the memory its running processes use. These changes improve both, through different mechanisms.

The everyday experience: use Alt + Space, search, then open an app or file as usual. Quick reopening reuses the popup. After a longer break, Torchlight recreates the interface while the search index stays ready.

The two charts use different baselines and different units of resource use. Their percentages cannot be added together. Disk totals exclude the development checkout, build artifacts and shared system libraries.

02 /

The changes, one by one.

The first round reduced installed size and released hidden-window resources. The latest round added a lifetime limit for the popup.

01Release programs

Keep only the code each program needs.

The linker removes unused code from release executables. Installation removes debugging information from the shipped files; diagnostic builds remain available.

Build→Drop unused code→Strip debug data

32.98 → 7.18 MiB across the three installed executables in the earlier round: 78.2% smaller. This is mainly a disk saving.

02Unused local data

Remove the semantic cache and model.

Semantic search was disabled on this computer. We explicitly removed its 109,415 cached records, compacted the database and deleted the unused model file.

Database: 555.03 → 10.31 MiB.
Model: 62.32 → 0 MiB.
File identities, indexed roots and launch history were preserved. Name/path search continues normally.

03Optional cache layout

Store retained vectors with less wasted space.

For installations using semantic search, schema v5 uses a table layout better suited to its vector records. The same vector bytes and unique keys are preserved.

Synthetic cache experiment: 480.84 → 149.36 MiB, about 69% smaller. This is a separate layout comparison; it adds no further saving to this computer’s already-purged cache.

04On dismissal

Release the hidden window’s resources.

Hiding clears the preview and releases the native window surface and renderer. After 500 ms hidden, the allocator is asked to return unused heap pages to the operating system.

The application and widgets initially stay alive for fast reuse. Quick reopening cancels the delayed allocator step. The graphics renderer choice remains unchanged.

05Latest · idle exit

End the popup after a one-minute break.

A 60-second hidden timer ends the UI process, releasing its remaining process memory. Reopening cancels the timer. A visible popup never expires.

121.60 → 55.56 MiB combined background RAM in the native observation. The daemon keeps its file index, available-app catalog and filesystem watchers.

06Maintenance & evidence

Make cleanup explicit and measurable.

Added read-only storage reporting, locked offline semantic cleanup, migration regressions, memory profiling and before/after popup benchmarks.

Cleanup checks preserve data and catch interrupted writes. These tools establish evidence; they do not themselves produce an additional RAM saving.

About semantic search: the unused model and cache were removed from this installation. The optional feature still exists in the code. Using it again requires a model and explicit configuration; other users’ caches are not silently deleted.

Related requested changes also remain in place: Web actions use each user’s system default browser, app discovery hands installation to Software/Discover, and the “P100” header label is removed. These are functional/UI changes, not claimed memory savings.

03 /

The popup rests. Search stays ready.

Torchlight has two separate jobs: the popup draws what you see, and the daemon searches and watches your files. Ending the popup leaves the daemon working.

BEFOREHide the window → retain the popup process indefinitely → continue paying its background RAM cost.
1 · VISIBLESearch normally

The popup and search service run together. No idle exit while visible.

2 · HIDDENKeep it ready briefly

Release window resources; keep the popup process for up to 60 seconds.

3 · IDLEExit the popup

Release the UI process’s memory. The search service continues running.

4 · NEXT SHORTCUTCreate a fresh popup

Rebuild the interface and connect to the existing index.

Shortcut pressed during step 2? Return directly to step 1 and cancel idle exit. The next dismissal starts a new countdown.

After the timeout: only the search service remains. The measured combined background usage was 55.56 MiB on this computer.
Already-launched apps keep running. Browser windows, files opened in other apps and the Software manager continue independently of the popup’s normal exit.
Does reopening cause a memory spike?

RAM rises again while the interface starts. Each previous popup process has ended, so its old process memory does not accumulate across restarts. A temporary startup peak above normal running usage is possible.

The highest instantaneous startup peak has not been measured. The reported RAM numbers are settled observations; the extra startup time alone does not establish the size of a peak.

Shutdown safeguards and the option to stay resident

Pending launch completion and history IPC postpone shutdown. Reopening also cancels an asynchronous service-policy check. A custom systemd service that might kill child apps or restart the popup makes Torchlight stay resident; unknown settings are handled the same way.

To keep the popup resident, use torchlight-gtk --idle-exit-seconds=0 --toggle. Values from 1 to 86400 set another delay. Add the option to the shortcut command if it should apply to future launches too.

06 /

What can improve next?

These are follow-up opportunities. Their benefits are not included in the savings above.

  1. Measure the reopening peak. Sample startup memory at a fine interval, repeatedly, to establish the transient peak and how quickly it settles. This directly answers the remaining “memory spike” question.
  2. Reduce RAM during active and continuously warm use. The latest change meets a sub-100-MiB idle total on this workload. The earlier sub-100-MiB warm-total target remains open, and GL growth still needs attribution across configurations.
  3. Compact indexes and the available-app catalog. Profiles identify sizable prefix, file, trigram and typo structures. Representation changes need comparisons that preserve relevance and latency. No such algorithm change was made in this round.
  4. Evaluate renderer choices on actual hardware. A lighter rendering path may save RAM, but visual differences and native driver behavior need testing. Torchlight continues to use its existing renderer policy.
The current balance: low memory after a break, familiar fast reuse during quick interactions, and a small measured reopening delay after the popup exits.
07 /

Definitions and the source record.

MiB / KiB
Binary units: 1 MiB is 1,048,576 bytes; 1 KiB is 1,024 bytes. These are used consistently for disk and RAM here.
PSS versus RSS
PSS divides shared memory among its users. RSS counts mapped resident pages in each process. The headline RAM comparison uses PSS.
Warm versus fresh
Warm means reusing an existing popup process. Fresh means starting a new process; operating-system caches may still be warm.
Median / p95
Median is the middle sample. p95 describes the slower end of the measurements; small samples make it less stable.
Daemon
The background search service. It maintains the index and watches for changes even when the popup is closed.
Memory boundaries
Process PSS is not GPU VRAM or the change in system-wide free memory. A service total can also include launched child apps and file cache.
