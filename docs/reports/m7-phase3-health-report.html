Torchlight · Health report · M7 Phase 3

Did Phase 3 close the open items?

The Phase 2 report left three results out of range. Phase 3 changed how Torchlight handles bursts of changes, how it cleans up after rescanning a folder, and how it keeps its in-memory copy of the database. Like a blood test, this report lists each measurement with the range it should fall in, a flag, and the value before the change. Plain-language definitions are at the end.

Overall result

Fixed, with three follow-ups

All three red flags from Phase 2 are fixed on the benchmark copy and on your live service. A burst of 20,000 new files is searchable 0.44 s after it is written instead of 3.0 s, and renaming its folder 0.43 s instead of 2.1 s. Search is ready 0.11 s sooner after a restart (within 2.3% of the build before Phase 2). A change directly in your home folder no longer costs database work (0.24 s before). The ledger shrank from 12.6 to 8.5 MB. Search speed, small-change lag, idle cost and correctness are unchanged. Three results are out of range: memory after a rebuild reads 10.2 to 10.8% above everyday memory, because everyday memory fell more than the rebuild figure; peak memory during a big change is 4 to 6 MB higher for about 1.6 s; and your desktop's background CPU is at 0.25 to 0.27%, from parts this phase did not touch.

3Red flags and things to know

Anything out of range, anything found and fixed while validating, and the trade-offs that come with the change, each explained in plain words.

Red flagMemory after a rebuild reads 10.2 to 10.8% above everyday memory (limit 10%)

What we saw. After the event tests and a full rebuild, memory was 184 to 185 MB, 3 to 4 MB less than the old build (188 MB). But everyday memory also fell, by 5 MB (172 to 167 MB, the smaller ledger), so the growth measured against it rose from 9.3% to 10.2 to 10.8%.

Why. The gate compares two numbers that both went down, the smaller one by more. A rebuild without the events before it grows about 8% in both builds, and a trim afterwards returns at most 1 MB, so the extra is not memory the program forgot to give back.

What it means for a user. Nothing worse than before: the daemon uses less memory than the old build at every moment measured. Decision needed: keep the gate as it is (and look for 1 to 2 MB of fragmentation), or restate it against the previous build's absolute memory.

Red flagPeak memory during a big change is 4 to 6 MB higher, for about a second and a half

What we saw. The highest memory during the 20k burst was 378 MB instead of 374 MB, and during the rename 390 MB instead of 384 MB.

Why. A big change is now made searchable first, as a quick update, and the full rebuild follows. While the rebuild runs, the quick update (about 22,000 entries) is still in memory next to the old and the new index. Before, the old and new index existed together without it, but the change only became searchable after the rebuild.

What it means for a user. A big change shows up in search 2 to 3 seconds sooner, at the cost of a few extra megabytes for about 1.6 s. This is the trade-off ADR 0045 accepts.

Red flagYour desktop's background CPU is about 0.25%, at its limit, but no longer from folder rescans

What we saw. Two samples on the new build read 0.265% (10 minutes) and 0.253% (15 minutes) of one core. This morning, on the old build, a quiet 10 minutes read 0.157%. The windows differed in activity: 1 folder rescan, then 6.

Why. The cost the Phase 2 report found (about 0.24 s of database work for every change in your home folder) is gone: the same test now costs nothing measurable. What is left is spread over parts Phase 3 did not touch: the app list's change check (0.07 to 0.09%), the main loop (0.06%), the indexing loop and its rescans (0.06%), and the database thread (0.04%), most likely its once-a-minute history clean-up (the live service cannot be profiled here). The benchmark copy idles at 0.14% on both builds.

Suggested next step: measure the app list's once-a-second check and the 41 wake-ups per second (already listed as later work) on the live desktop, with longer samples.

WatchThe full check is 3 to 6% under its 1-second target

Three rounds of five checks: medians 943, 952 and 969 ms (the old build 993 to 1,021 ms today). Path hashing and lookups got cheaper; what is left is almost all the kernel reading file details (statx 39% of the indexing thread, listing folders 12%, the walker's own folder stat 7%). The next lever is a walker that reads details relative to each open folder instead of by full path.

WatchTyping latency at 500k is close to 5 ms on today's busy machine

Measured three times each, alternating with the old build on the same machine: 4.54 to 4.77 ms against 4.63 to 5.14 ms. Phase 2 recorded 3.74 ms on a quieter day; the search code did not change. Background load (the machine's load average was about 3.4) moves both builds alike.

WatchFree memory held back after events is at its 5 MB limit

5 MB in all three runs (the old build 4 to 5 MB). Unchanged from Phase 2, still with little room.

Good to knowUnder a continuous stream of changes, a new name can take up to a second to appear

To index a burst in one pass, Torchlight now waits until changes pause for 0.1 s, but never more than 1 s after the first one. A single change still shows up after about 0.1 s. While something keeps writing new names (for example, a long download of many files), new names appear about once a second instead of every 0.1 to 0.2 s. Once 512 folders are waiting, it rescans at once, so a large deletion stays fast.

Good to knowA change that arrives during the follow-up rebuild waits for it

After a big change, the full rebuild (about 1.6 s at 213k) runs as soon as nothing else is waiting. A change made during those 1.6 s is indexed right after it. Before, the same rebuild ran before the big change itself became searchable.

ResolvedFound while validating: settling turned a big deletion into a full check

What happened. The first version waited for every burst to settle, so deleting the 22k tree collected more than 1,024 changed folders and fell back to checking everything: 1.2 s instead of about 0.1 s.

Fix. Settling stops once 512 folders are waiting. Deletions now take 1 to 159 ms, faster than before. A new writer test deletes 1,100 folders in batches and fails if a full check runs.

ResolvedFound by a test: the follow-up rebuild could not be published

The rebuild that follows a big change shows the same saved catalog generation as the quick update it replaces, and publication refused an equal generation. The writer test caught it (the rebuild never happened). The rebuild now uses a publication call that accepts the same generation and still refuses older ones; a catalog test checks both views answer identically.

Good to knowBursts were already split before Phase 2 on a busy machine

Today the build from before Phase 2 needed two full rebuilds in 6 of 8 bursts (median 2,805 ms), not the 1 in 8 the Phase 2 report saw. Whether a burst is caught in one pass depended on timing; Phase 3 makes it independent of it.

4Definitions

Daemon (torchlightd)
The background program that keeps the file list and answers searches.
Index / catalog
Torchlight's list of every file and folder name, kept in a SQLite database on disk and in memory for fast search.
Full check (full scan)
Walking every file and folder to make sure the index is exactly right: at startup, once an hour, and after missed notifications.
Folder rescan (scoped scan)
Re-checking only the folder where a change was reported.
Burst
Many file changes in a short time, such as unpacking an archive or cloning a repository.
Settle window
New in Phase 3: after a change, Torchlight waits until changes pause for 0.1 s (at most 1 s) before rescanning, so a burst is read in one go.
Quick update (delta)
A small extra index for the entries that changed since the last full rebuild, searched together with the main index.
Full rebuild (compaction)
Rebuilding the whole in-memory index from the database, folding the quick update into the main index (about 1.6 s at 213k entries).
Deferred rebuild
New in Phase 3: a big change is published as a quick update first, and the full rebuild follows once nothing else is waiting.
Ledger (persisted-state map)
A compact in-memory copy of what the database holds, one fingerprint per entry, so a check can skip unchanged files.
Folder cleanup
After a folder rescan, deleting the saved entries of children that are gone. Phase 3 makes it look only at the folder's direct children.
inotify / watch
Linux's change notification service; Torchlight registers one watch per folder.
CPU-second (CPU-s)
One second of one processor core working flat out.
% of a core
Average share of one processor core over a window. 100% means one core busy all the time.
RSS / peak memory (VmHWM)
How much RAM the program occupies now / the most it has occupied since it started.
Free memory held back
Memory the program freed but the C library kept instead of returning it to the system.
Sanitizers (ASan, UBSan, LSan)
Special test builds that stop at the first invalid memory access, broken C rule, or leaked block.
Mutation check
Deliberately breaking a fix to confirm the test that guards it fails.
Equivalence test
Applies the same random file changes to the old and new way of scanning and requires identical databases.
p50 / p95
Percentiles: p50 is the typical case, p95 the slow 5%.
-O3 / -O0 build
Optimized (benchmark) versus unoptimized debug build. Your live service runs the debug build.

5How this was measured

Scenario panels come from tests/bench/bench_scenarios.py, which starts an isolated daemon per phase (own database, config and socket; the host's application list; history on) on a mirror of the data as empty files, and reads CPU per thread, I/O, memory and wake-ups from /proc. The HEAD and Phase 3 optimized builds (-O3, frame pointers) ran back to back on the same trees with the in-repo CPU sampler attached. Noisy numbers (bursts, renames, readiness, queries, the memory gates) were repeated, alternating the builds.

Details and raw data
  • Machine: Intel i7-8700K (6 cores, 12 threads), 32 GB, Linux 6.8, ext4 on LVM, a desktop in use (load average about 3). perf is locked here, so CPU profiles use the in-repo LD_PRELOAD sampler; system call counts use strace -f -c.
  • Scenario runs: 2026-10-12-m7p3-213k-base.jsonl and -new.jsonl (all phases), -494k-*.jsonl, the events phase three more times per build (-213k-events-*.jsonl) and the queries phase twice (-213k-queries-*.jsonl).
  • Repeated single-purpose runs (bursts and renames ×7, restarts ×6 for three builds, root-folder lag, full checks, queries after bursts, the rebuild alone, the 30-check memory trend, the sanitized daemon) and the live-service samples: 2026-10-12-m7p3-repeats.jsonl.
  • make bench: 2026-10-12-m7p3-lexical.txt, plus three alternating runs of both builds at 500k.
  • Live service: the probe creates and deletes a hidden file directly in the home folder; idle samples read the daemon's CPU per thread from /proc over 10 and 15 minutes of ordinary desktop use.
