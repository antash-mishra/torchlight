3Red flags and things to know

Anything out of range, anything found and fixed while validating, and the trade-offs that come with the change, each explained in plain words.

Red flagA burst of 20,000 new files becomes searchable about 1.3 s later

What we saw. Writing 20,000 files into 2,000 new folders in under a second: the last file became searchable after 3,002 ms instead of 1,672 ms (median of 7 runs each). Total CPU for the whole event is about the same (+7%).

Why. The daemon catches up in two passes. The new crawl is faster, so its first pass finishes reading the still-growing folder tree sooner and leaves more files for the second pass. That pass is then too big for a quick update of the search index and needs a full index rebuild (about 1.3 s). Before, the second pass was small enough for a quick update in 7 of 8 runs. A folder that appears all at once (a rename or move) is not affected (+6%).

What it means for a user. After unpacking a large archive or cloning a big repository, the last files show up in search a second or so later than before. Nothing is lost. Suggested fix: let a burst of changes settle (for example, wait until no event arrived for 100 ms, at most one second) before rescanning, so a burst is indexed in one pass.

Red flagSearch is ready about 0.2 s later after a restart

What we saw. After a restart the daemon answered after 1,524 ms instead of 1,325 ms (median of 6 restarts each).

Why. While loading the saved index it now also fills the new in-memory map (two path fingerprints per entry) and reads three more columns per row: about 0.2 s of extra work before the daemon starts listening. In return the full check that follows is 2 s shorter.

Suggested fix: open the socket before the saved index loads, as the M7 plan already lists, or build the map while the startup check runs.

Red flagBackground CPU on your desktop is above the Phase 1 level (an existing cost, not from Phase 2)

Your live service averaged 0.34% of a core over its idle sample, more than the 0.25% of the Phase 1 review (the old build used about 0.35% earlier today, not counting its startup and hourly checks). Creating and deleting one file directly in your home folder costs the database thread about 210 ms; in a small folder, nothing measurable. Each rescan of the home folder's own entries runs a cleanup query over the path range of the whole catalog. That query is unchanged by Phase 2 (an existing cost found while validating). Apps that save hidden files in your home folder trigger it.

Suggested fix: limit the cleanup to the folder's direct children with an index on the parent folder, or compare the folder's children in memory.

WatchThe full check meets its 1-second target only narrowly

The dedicated run measured a median of 978 ms (target ≤ 1,000 ms). The same scan code measured 1,028 ms in an earlier run and 991–1,064 ms during the 30-scan memory test (with other work running). What is left is almost all the kernel reading 213,000 file details (Panel 1b). The next lever, if needed, is the plan's optional walker that reads details relative to each open folder instead of by full path.

WatchTwo memory gates are close to their limits

Free heap held back after the event tests is 5 MB (limit 5 MB; before 3 MB), and memory after a rebuild is 9.9% above steady (limit 10%; before 5.1%). The rebuild test adds up to 64,000 entries, and the new map grows with every entry (about 60 bytes each), which the old build did not have. Both pass, with little room.

WatchThe new in-memory map uses more memory than the plan estimated

The plan estimated about 5 MB at 213k entries; the map needs 12.6 MiB (32 bytes per entry plus a hash index kept at most half full), and 27.2 MiB at 494k entries.

Everyday memory still went down (Panel 6), because full checks no longer copy every path, and the live service uses less memory than before (Panel 9). A sorted array instead of the hash index would roughly halve the map if larger catalogs need it.

WatchA replaced folder's contents disappear from search for about a tenth of a second

If a folder is deleted and a new one with the same name receives the same files, the database correctly forgets the old folder's contents. The old scan wrote them back in the same step; the new one does it in a quick follow-up pass. It needs this exact pattern while no change notification arrived (startup or recovery) and heals itself; a dedicated test fails if the follow-up pass is removed.

ResolvedFixed while validating: unchanged checks still wrote to a scratch file

What happened. Profiling the new build showed about 15 MB written to SQLite's scratch file on every unchanged full check after a first-ever index. SQLite keeps three small bookkeeping tables per scan. They were emptied inside each scan's transaction, and an unchanged scan is rolled back, so the rollback restored them and the next scan emptied them again.

Fix. The tables are now emptied outside any transaction. A new daemon test fails with the old behaviour (1.1 MB written for 6,000 files) and passes with the fix.

ResolvedFixed while validating: large deletions became visible later

After each commit the in-memory map reloaded the changed rows before the search index was updated. For a 22,000-entry deletion that delayed visibility (344 ms against 219 ms). The reload now runs after publication; repeated runs show the difference gone into noise (Panel 5).

ResolvedPrevented: a glibc shortcut that can silently skip whole folders

Skipping per-file checks in the folder walker (Step 2.1) also switches on an old shortcut that guesses how many sub-folders a folder has from its link count. On filesystems that report link counts wrongly (some network and FUSE drives) whole sub-trees would never be visited. Reproduced on this machine, then the guess was turned off for every folder.

Good to knowThe daemon still wakes about 41 times a second when idle (unchanged, not in scope)

Two 50 ms polling loops. It costs very little CPU (Panel 4) but keeps the processor from its deepest sleep; the M7 plan lists it as later work.

Good to knowYour live service runs the unoptimized debug build

Panel 9 comes from the -O0 build your systemd unit starts. The optimized build is about 1.5× faster on CPU-bound work (Panels 1 to 7). Switching the unit to an optimized build would make every remaining scan cheaper still.

Good to knowOne random test missed a case at first; a deterministic test now covers it

Disabling the follow-up pass for replaced folders did not make the random equivalence test fail: random changes rarely produce that exact pattern. A deterministic test was added that fails without it, and the random test was also run with eight more seeds. All passed.

Good to knowStep 2.4 (skip unchanged folders) is not needed

The full check meets its targets (978 ms at 213k, 1,859 ms at 494k), so the optional step that would weaken what the hourly safety-net scan verifies stays out.

4Definitions

Daemon (torchlightd)
The background program that keeps the file list and answers searches. It runs all the time, so every bit of work it does costs battery and heat.
Index / catalog
Torchlight's list of every file and folder name it can find, kept on disk in a SQLite database and in memory for fast search.
Full scan (full check)
Walking every file and folder to make sure the index is exactly right. Runs at startup, once an hour as a safety net, and after events the change notifications missed.
Scoped scan
Re-checking only the folder where a change was reported, about 0.1 s after the change.
inotify / watch
Linux's change notification service. Torchlight registers one watch per folder and Linux tells it when names in that folder change. The kernel limits how many watches a user may hold.
CPU-second (CPU-s)
One second of one processor core working flat out. 1 CPU-s spread over an hour is 0.03% of one core.
% of a core
Average share of one processor core used over a time window. 100% means one core busy all the time.
RSS (resident memory)
How much RAM the program actually occupies right now, in megabytes (MB = MiB here).
Peak memory (VmHWM)
The highest RSS the process has reached since it started (its high-water mark).
Memory leak
Memory the program allocates and never gives back. Over days a leak makes the program grow without limit. LeakSanitizer lists every such block when the program exits.
Sanitizers (ASan, UBSan, LSan)
Special test builds that stop the program at the first invalid memory access (AddressSanitizer), broken C rule (UndefinedBehaviorSanitizer) or leaked block (LeakSanitizer).
System call
A request from the program to the Linux kernel, such as 'tell me about this file' (stat) or 'list this folder' (getdents64). Fewer calls means less work.
stat / statx
The system call that reads a file's details: size, time stamps and identity.
SQLite temp file
A scratch file SQLite writes to when a query's working data does not fit in memory. The old full scan wrote about 100 MB to one each time.
p50 / p95 / p99
Percentiles. p50 is the typical (median) case; p95 means 95% of cases were at least this fast, so it describes the slow 5%.
Wake-ups per second
How often the daemon's threads wake from sleep. Each wake-up keeps the processor from its deepest power-saving state.
Persisted-state map (ledger)
New in Phase 2: a compact in-memory copy of what the database holds, one fingerprint per file, so a full scan can tell unchanged files apart without asking the database.
Signature
A 64-bit fingerprint of a file's saved details (kind, size, modification time, identity). Equal signatures mean nothing changed.
Exhaustive mode
The old way of scanning (every entry written to the database), kept as a test switch so the new way can be compared against it.
Equivalence test
A test that applies the same random file changes under the old and the new scanning and requires both databases to end up identical.
Mutation check
Deliberately breaking a fix to confirm the test that guards it fails; proves the test works.
-O3 / -O0 build
Optimized (benchmark) versus unoptimized debug compilation. Your live service runs the debug build, about 1.5x slower on CPU-bound work.
Reference range
The acceptable values for a measurement: from the M7 plan's exit criteria, the Phase 1 gates, or (marked) a limit chosen for this report.

5How this was measured

All panels except 8 and 9 come from tests/bench/bench_scenarios.py, which starts an isolated daemon per phase (own database, config and socket; the host's application list; history on) on a mirror of the data as empty files, and reads CPU per thread, I/O, memory and wake-ups from /proc. The old and new optimized builds (-O3, frame pointers) ran back to back on the same trees with the in-repo CPU sampler attached.

Details and raw data
  • Machine: Intel i7-8700K (6 cores, 12 threads), 32 GB, Linux 6.8, ext4 on LVM. perf is locked here, so CPU profiles use the in-repo LD_PRELOAD sampler; system call counts use strace -f -c on two runs (start only, start plus three forced scans) and report the difference per scan.
  • Full checks were forced with reconcile on an idle daemon, five times, median reported; peak watches and SQLite temp files were sampled every 50 ms from /proc/PID/fdinfo.
  • Leak check: the sanitizer build of the daemon on the 213k mirror (cold index, three forced scans, 2,000-file burst, rename, delete, queries), stopped with SIGTERM so LeakSanitizer reports at exit; plus the full make test suite under ASan, UBSan and LeakSanitizer.
  • Memory trend: 30 forced full scans in a row on the optimized build, RSS read 1.5 s after each.
  • Live service: three forced scans before and after restarting the installed unit on the new build, and 20 minutes of ordinary desktop use afterwards.
