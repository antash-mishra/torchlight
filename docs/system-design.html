How Torchlight works

Torchlight is a Spotlight-style launcher for Linux. You press a shortcut, type a few letters, and open an app, a settings panel, a file or a folder. This page explains the pieces behind that popup, how they talk to each other, and why typing stays fast.

Based on the code and docs at commit da125c3, October 2026. The architecture doc has the full technical detail.

1The short version

Torchlight is three programs. Only one of them does the real work.

the brain

torchlightd, the daemon

Runs in the background all the time. It keeps every file, folder and app name in memory, watches your folders for changes, and answers searches.

the face

torchlight-gtk, the popup

The window you see. It sends what you type to the daemon, shows the results, and opens whatever you pick.

for terminals and scripts

torchlight, the command line

The same searches from a terminal, plus status, reconcile (rescan) and history-clear.

The main idea: the popup never searches by itself. All searching happens in the daemon, which already has everything loaded in memory. So the popup can appear instantly, and each keystroke is answered in a few milliseconds, even with half a million files.

Only names and paths are indexed. Torchlight never reads what is inside your files.

2The big picture

Read the diagram from top to bottom: what you see on screen, the private connection in between, the daemon's moving parts, and the files on disk.

In plain words

  1. You press the shortcut. The popup appears with an empty search box. (There is only ever one popup; pressing the shortcut again hides it.)
  2. Each keystroke becomes a small message sent through a Unix socket: a private, local connection that only your own user account can open.
  3. Inside the daemon, the IPC thread receives the message and hands it to the search thread, which looks it up in the in-memory index and sends back the best matches.
  4. In the background, the indexing thread notices file changes, the persistence thread saves them to a SQLite database, and the desktop worker keeps the list of installed apps current. Each publishes a fresh, read-only version of the index when it's ready.
  5. When you press Enter, the popup itself opens the app, file or folder. The daemon only checks that the result is still valid and remembers what you opened.

3What happens when you type

Here is one search and one launch, step by step. Time runs downward.

Three rules keep it fast and safe

nothing slow

The search path does no slow work

While searching, the search thread never reads the disk, never runs SQL and never asks the system for new memory. Everything it needs, including scratch space, is prepared in advance.

newest wins

Old keystrokes are cancelled

If you type faster than answers come back, a newer query cancels the older ones still queued or running. The popup also ignores any late answer for text you have already changed.

check first

Results are checked before opening

Results carry an id, not just a path. Before launching, the popup asks the daemon whether that id is still current, so a file that was moved or deleted is never opened by mistake.

Under the hood: what the messages look like

Each message is one line of JSON. A request (at most 8 KiB) looks like this:

{"version":1,"request_id":"7","op":"query","query":"prjnts","limit":10}

The answer, trimmed, from a real daemon:

{"version":1,"request_id":"7","phase":"final","catalog_gen":1311,
 "search_id":"e9e4…:52","status":"ok","reason":"lexical_only",
 "indexing":{"active":false,"degraded":false, …},
 "history":{"enabled":true, …},
 "results":[{"id":"12666","kind":"file",
             "display":"/home/you/notes/projectNotes.md",
             "path":"/home/you/notes/projectNotes.md"}],
 "timing":{"engine_us":1460}}
  • Operations: query, status, resolve, open, reconcile and history_clear.
  • Paths are raw bytes on Linux. A path that is not valid UTF-8 is sent as path_b64 instead of path; display is only for showing, never for opening.
  • Ids are strings so no JSON client loses precision on 64-bit numbers.
  • Limits keep one bad client from hurting others: 16 clients, 4 open requests and 1 MiB of queued output per client, and a 5-second deadline for slow clients.
  • With the optional semantic model, a query gets two answers: a fast lexical one, then a final one. Without it (the default) there is one final answer with reason: lexical_only.

4How a search finds matches

Comparing your text with half a million names one by one would be too slow. So when the index is built, the engine also builds several lookup tables. A search uses them to find a short list of candidates, then scores only those.

  1. Split into words. Every word you type must match either the name or one of its parent folders. So work notes finds notes.md inside a work folder. A word containing / can match across the whole path.
  2. Find candidates four ways. Prefix catches the start of a word, subsequence catches abbreviations, trigram catches a piece from the middle, and typo catches one wrong, missing, extra or swapped letter.
  3. Score. Each candidate gets a score for how well the letters line up: at word starts, next to each other, without big gaps. Torchlight uses Frizbee, a fast fuzzy matcher (a vendored Rust library using SIMD instructions) for this. Each folder is stored once and scored once, not once per file inside it.
  4. Rank. An exact path beats an exact name, and both beat everything else. Apps and settings have their own small engine and are merged with files by score. Things you open often get a small, capped boost, so history can reorder results but never bury an exact match.

5How the index stays up to date

Your files change all the time. Torchlight follows those changes without rescanning everything, and without making any search wait.

  1. Linux's inotify tells the indexing thread that something in a folder changed.
  2. It waits 100 ms, so a burst of changes (unzipping an archive, a git checkout) becomes one update, and notes which folders were touched.
  3. It rescans only those folders, not your whole home folder.
  4. It hands the batch to the persistence thread, which saves it in one short SQLite transaction and reports which rows changed. No scanning or index building happens while the database is locked for writing.
  5. The indexing thread builds a small delta index of just the changed entries and publishes a new version. The version number, catalog_gen, goes up by one.
  6. The next keystroke searches the new version. Searches already running finish on the old one.

Safety nets

startup

The daemon loads the saved catalog from SQLite and starts answering right away. A full rescan then runs in the background to catch anything that changed while it was off.

every 30 seconds

A full background rescan repairs anything the watcher missed, such as folders it could not watch. Change the interval with --rescan-ms.

big changes

When the delta grows past max(4096, base/32) entries, the indexing thread rebuilds a fresh base index from SQLite (compaction), again on the side.

watcher trouble

If inotify cannot be set up, Torchlight keeps going with periodic rescans only, and torchlight status reports the reduced coverage.

6Snapshots: why searches never wait

The search side and the indexing side share data without blocking each other. The trick is that the index is never changed in place.

Each version of the index is a read-only snapshot with a number, catalog_gen. A search leases the current snapshot when it starts and returns it when it's done. The indexing thread builds the next snapshot privately, then publishes it with a single pointer swap, so there is never a half-updated index to see. Apps and settings work the same way, with their own snapshots from the desktop worker.

7Where data lives

SQLite is the lasting copy. The in-memory index is rebuilt from it when the daemon starts, and searches only ever read memory.

In memory, inside the daemon

  • Files & folders snapshot: every indexed path, the lookup tables for the four channels, and a tree of folders (each folder stored once).
  • Apps & settings snapshot: names, generic names and keywords from .desktop entries.
  • Usage summary: how often and how recently you opened things, and which typed query led to which open. Capped in size.
  • Client queues: a small, bounded queue per connected client.

On disk

  • ~/.local/share/torchlight/catalog.db: the SQLite database. Tables files, roots, searches, opens, desktop_opens and meta. Paths are stored as raw bytes.
  • ~/.config/torchlight/config: which folders to index (root =) and which hidden folders to include anyway (allow =).
  • $XDG_RUNTIME_DIR/torchlight.sock: the socket, readable only by you, plus lock files that stop a second daemon from starting.

Privacy: only names and paths are stored, never file contents. History stays on your machine, is kept for 30 days by default (--history-days), and can be turned off (--no-history) or erased (torchlight history-clear). Hidden folders and node_modules, target, build and __pycache__ are skipped unless you allow them.

9Extras around the core

X11 only

Open windows under their app

Each time the popup opens, it reads the list of open windows itself and shows them beneath the matching app result, matched by the app's wm_class. Enter switches to the most recent window. The daemon never sees your windows.

off by default

Semantic search

With --model PATH.tlm, a small local Potion model also matches by meaning. The daemon sends the normal results first, then a merged "final" list. It works, but it is parked because it is slower on large catalogs.

no daemon needed

Offline mode

With the daemon stopped, torchlight index scans into SQLite and torchlight query --db … searches it directly. A lock file stops this from racing a running daemon.

11Words you'll see

Daemon
A program that runs in the background without a window. Here, torchlightd.
Unix socket
A private connection between programs on the same computer, opened like a file.
Snapshot
One complete, read-only version of the index. Replaced as a whole, never edited.
catalog_gen
The version number of the files snapshot. It goes up by one with every publish.
Lease
A search's hold on a snapshot. A snapshot is freed only when no search holds it.
Base and delta
A snapshot's big shared part, and its small part with recent changes.
Tombstone
A marker that hides a base entry because it changed or was deleted.
Compaction
Rebuilding a fresh base once the delta gets big.
Channel
One way of finding candidates: prefix, subsequence, trigram or typo.
Trigram
A three-letter piece of a name, like rep, epo, por in report.
inotify
The Linux feature that tells a program when files in a watched folder change.
Frecency
A score that mixes how frequently and how recently you opened something.
Resolve
Checking a result's id against the current index right before opening it.
