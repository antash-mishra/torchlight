Torchlight · system design

How Torchlight works

Torchlight is a Spotlight-style launcher for Linux. You press a shortcut, type a few letters, and open an app, a settings panel, a file or a folder. This page explains the pieces behind that popup, how they talk to each other, what they do over a day, and how fast and quiet they are, with charts drawn from real measurements.

Based on the code at commit 4490e26 (M7 Phase 3) plus M8 (ranking files by place, excluded folders), 12 October 2026. Numbers come from the reference machine (a 6-core Intel i7-8700K with 32 GB of memory) and a 213,000-entry copy of a real home folder, unless a chart says otherwise. The architecture doc has the full technical detail, and the Phase 2, Phase 3 and M8 health reports every measurement.

1The short version

Torchlight is three programs. Only one of them does the real work.

the brain

torchlightd, the daemon

Runs in the background all the time. It keeps every file, folder and app name in memory, watches your folders for changes, and answers searches.

the face

torchlight-gtk, the popup

The window you see. It sends what you type to the daemon, shows the results, and opens whatever you pick.

for terminals and scripts

torchlight, the command line

The same searches from a terminal, plus status, reconcile (rescan) and history-clear.

The main idea: the popup never searches by itself. All searching happens in the daemon, which already has everything loaded in memory. So the popup can appear instantly, and each keystroke is answered in a few milliseconds, even with half a million files.

Only names and paths are indexed. Torchlight never reads what is inside your files.

3The big picture

Read the diagram from top to bottom: what you see on screen, the private connection in between, the daemon's moving parts, and the files on disk.

In plain words

  1. You press the shortcut. The popup appears with an empty search box. (There is only ever one popup; pressing the shortcut again hides it.)
  2. Each keystroke becomes a small message sent through a Unix socket: a private, local connection that only your own user account can open.
  3. Inside the daemon, the IPC thread receives the message and hands it to the search thread, which looks it up in the in-memory index and sends back the best matches.
  4. In the background, the indexing thread notices file changes, the persistence thread saves them to a SQLite database, and the desktop worker keeps the list of installed apps current. Each publishes a fresh, read-only version of the index when it's ready. The indexing thread also keeps a ledger, a compact list of what the database holds, so a check of every folder can skip the files that did not change (Full checks).
  5. When you press Enter, the popup itself opens the app, file or folder. The daemon only checks that the result is still valid and remembers what you opened.

4A day in the life

Most of the time Torchlight sleeps. It wakes up when you search, when a name changes in one of your folders, and once an hour for a safety check.

When you log in

The daemon first loads the saved list of names from its database into memory; searches wait during this step. Then it starts answering searches, while a full check runs in the background to catch anything that changed while it was off.

How often a full check runs

A full check walks every indexed folder and compares what is on disk with what is saved. Normally Torchlight rescans only the one folder where a name changed, so full checks are kept for moments when a change could have slipped past:

5What happens when you type

Here is one search and one launch, step by step. Time runs downward.

Three rules keep it fast and safe

nothing slow

The search path does no slow work

While searching, the search thread never reads the disk, never runs SQL and never asks the system for new memory. Everything it needs, including scratch space, is prepared in advance.

newest wins

Old keystrokes are cancelled

If you type faster than answers come back, a newer query cancels the older ones still queued or running. The popup also ignores any late answer for text you have already changed.

check first

Results are checked before opening

Results carry an id, not just a path. Before launching, the popup asks the daemon whether that id is still current, so a file that was moved or deleted is never opened by mistake.

Under the hood: what the messages look like

Each message is one line of JSON. A request (at most 8 KiB) looks like this:

{"version":1,"request_id":"7","op":"query","query":"prjnts","limit":10}

The answer, trimmed, from a real daemon:

{"version":1,"request_id":"7","phase":"final","catalog_gen":1311,
 "search_id":"e9e4…:52","status":"ok","reason":"lexical_only",
 "indexing":{"active":false,"degraded":false, …},
 "history":{"enabled":true, …},
 "results":[{"id":"12666","kind":"file",
             "display":"/home/you/notes/projectNotes.md",
             "path":"/home/you/notes/projectNotes.md"}],
 "timing":{"engine_us":1460}}
  • Operations: query, status, resolve, open, reconcile and history_clear.
  • Paths are raw bytes on Linux. A path that is not valid UTF-8 is sent as path_b64 instead of path; display is only for showing, never for opening.
  • Ids are strings so no JSON client loses precision on 64-bit numbers.
  • Limits keep one bad client from hurting others: 16 clients, 4 open requests and 1 MiB of queued output per client, and a 5-second deadline for slow clients.
  • With the optional semantic model, a query gets two answers: a fast lexical one, then a final one. Without it (the default) there is one final answer with reason: lexical_only.

6How a search finds matches

Comparing your text with half a million names one by one would be too slow. So when the index is built, the engine also builds several lookup tables. A search uses them to find a short list of candidates, then scores only those.

  1. Split into words. Every word you type must match either the name or one of its parent folders. So work notes finds notes.md inside a work folder. A word containing / can match across the whole path.
  2. Find candidates four ways. Prefix catches the start of a word, subsequence catches abbreviations, trigram catches a piece from the middle, and typo catches one wrong, missing, extra or swapped letter.
  3. Score. Each candidate gets a score for how well the letters line up: at word starts, next to each other, without big gaps. Torchlight uses Frizbee, a fast fuzzy matcher (a vendored Rust library using SIMD instructions) for this. Each folder is stored once and scored once, not once per file inside it.
  4. Rank. An exact path beats an exact name, and both beat everything else. Among matches of similar strength, files closer to your indexed folder, and outside installed or vendored software, come first (see below). Apps and settings have their own small engine and are merged with files by score. Things you open often get a small, capped boost, so history can reorder results but never bury an exact match.

7How the index stays up to date

Your files change all the time. Torchlight follows those changes without rescanning everything, without making any search wait, and without doing anything at all for changes that leave every name as it was.

  1. Linux's inotify tells the indexing thread that a name in a folder changed: something was created, deleted or renamed. Saving a file changes no name, so Torchlight no longer even asks to hear about it.
  2. It waits 100 ms, so a burst of changes (unzipping an archive, a git checkout) becomes one update, and notes which folders were touched.
  3. It rescans only those folders, not your whole home folder.
  4. It hands the batch to the persistence thread, which saves it in one short SQLite transaction and reports which rows changed. No scanning or index building happens while the database is locked for writing. If the rescan only found new sizes or times, those are saved, but nothing is published: search never looks at them.
  5. The indexing thread builds a small delta index of just the changed entries and publishes a new version. The version number, catalog_gen, goes up by one.
  6. The next keystroke searches the new version. Searches already running finish on the old one.

What each kind of change costs

8Full checks, made cheap

Some moments need a look at every file, not just one folder: start-up, the hourly backstop, and anything that could have hidden a change. M7 Phase 2 (October 2026) did not make these full checks rarer. It made each one about four times cheaper.

Think of a librarian checking the shelves against the card catalog. The old way read each book's details twice, rewrote every catalog card even when nothing had moved, and then threw the new cards away. The new way keeps a short checklist in memory, the ledger, with one fingerprint per card. The librarian reads each book once, ticks it off, and touches the catalog only for books that are new, changed or missing.

9Health modes: healthy, repairing, fallback

Torchlight relies on Linux telling it about changes. When that works for every folder, there is almost nothing to do. When it can't, Torchlight covers the gap with rescans, and torchlight status says so.

Safety nets

start-up

The daemon loads the saved catalog from SQLite and starts answering right away. A full check then runs in the background to catch anything that changed while it was off.

every 30 seconds

Folders the watcher cannot cover are rescanned, and roots that were offline are checked. Failed walks stay in the repair set until a successful scan verifies recovery or deletion. With every folder watched there is nothing to do. Change the interval with --rescan-ms.

every hour

A backstop full check catches anything the watcher might have missed. Change it with --repair-ms; 0 turns it off.

something shifted

A mount appearing or going away at, inside or above an indexed folder, an inotify overflow, or torchlight reconcile triggers a full check at once. Mounts elsewhere, such as an hourly backup check, are ignored. A root that comes back online starts one at the next 30-second check.

big changes

When live delta entries exceed max(4096, base/32), the indexing thread rebuilds a fresh base from SQLite (compaction). Deletions hide entries without forcing this rebuild. Readers keep their old view until release; deleted base data stays allocated until a later rebuild.

watcher trouble

If inotify cannot be set up, Torchlight falls back to a full check every 30 seconds, and torchlight status reports the reduced coverage. Setting it up is retried on the same schedule.

torchlight status shows how many folders are in the repair set (repair_scopes), whether coverage is reduced (degraded), and why the last full check ran (last_full_reason: startup, reconcile, overflow, mount, backstop and a few rarer ones).

10Snapshots: why searches never wait

The search side and the indexing side share data without blocking each other. The trick is that the index is never changed in place.

Each version of the index is a read-only snapshot with a number, catalog_gen. A search leases the current snapshot when it starts and returns it when it's done. The indexing thread builds the next snapshot privately, then publishes it with a single pointer swap, so there is never a half-updated index to see. Apps and settings work the same way, with their own snapshots from the desktop worker.

When an old base is finally freed, or a full rescan is done with its list of every path, the daemon also hands that memory back to the system. Without this, the C library keeps freed memory for later and the daemon stays at its peak size: at 213k files it used to sit at about 434 MB after a burst of changes, and now settles at about 191 MB, close to its steady 167 MB (see the memory chart in Performance).

11Where data lives

SQLite is the lasting copy. The in-memory index is rebuilt from it when the daemon starts, and searches only ever read memory.

In memory, inside the daemon

  • Files & folders snapshot: every indexed path, the lookup tables for the four channels, and a tree of folders (each folder stored once, with its place penalty).
  • Apps & settings snapshot: names, generic names and keywords from .desktop entries.
  • Usage summary: how often and how recently you opened things, and which typed query led to which open. Capped in size.
  • Ledger: a fingerprint of every saved row, about 42 bytes each (8.5 MB at 213,000 entries). Full checks compare against it instead of the database.
  • Folder watches: one per indexed folder, 34,453 here, about 4 to 5 MB.
  • Client queues: a small, bounded queue per connected client.

On disk

  • ~/.local/share/torchlight/catalog.db: the SQLite database. Tables files, roots, searches, opens, desktop_opens and meta. Paths are stored as raw bytes.
  • ~/.config/torchlight/config: which folders to index (root =), which hidden folders to include anyway (allow =) and which folders never to index (exclude =).
  • $XDG_RUNTIME_DIR/torchlight.sock: the socket, readable only by you, plus lock files that stop a second daemon from starting.

14Extras around the core

X11 only

Open windows under their app

Each time the popup opens, it reads the list of open windows itself and shows them beneath the matching app result, matched by the app's wm_class. Enter switches to the most recent window. The daemon never sees your windows.

off by default

Semantic search

With --model PATH.tlm, a small local Potion model also matches by meaning. The daemon sends the normal results first, then a merged "final" list. It works, but it is parked because it is slower on large catalogs.

no daemon needed

Offline mode

With the daemon stopped, torchlight index scans into SQLite and torchlight query --db … searches it directly. A lock file stops this from racing a running daemon.

16Words you'll see

Daemon
A program that runs in the background without a window. Here, torchlightd.
Unix socket
A private connection between programs on the same computer, opened like a file.
Snapshot
One complete, read-only version of the index. Replaced as a whole, never edited.
catalog_gen
The version number of the files snapshot. It goes up by one with every publish.
Lease
A search's hold on a snapshot. A snapshot is freed only when no search holds it.
Base and delta
A snapshot's big shared part, and its small part with recent changes.
Tombstone
A marker that hides a base entry because it changed or was deleted.
Compaction
Rebuilding a fresh base once the delta gets big.
Channel
One way of finding candidates: prefix, subsequence, trigram or typo.
Trigram
A three-letter piece of a name, like rep, epo, por in report.
inotify
The Linux feature that tells a program when files in a watched folder change.
Repair set
Folders inotify can't keep track of (not watchable, not readable, or on a network or FUSE mount). They are rescanned every 30 seconds.
Backstop
The hourly full check of every root that catches anything the watcher missed.
Full check
Walking every indexed folder and comparing what is on disk with what is saved. Also called a full scan or full rescan.
Folder rescan
Re-reading just the one folder where a name changed. Most updates are this cheap kind.
Ledger
Torchlight's in-memory checklist of what the database holds: one fingerprint per saved row. It lets a full check skip unchanged files without asking the database.
Signature
A short number computed from a row's saved details (folder or file, size, modification time, identity). Equal signatures mean nothing changed.
Watch
A request to inotify to report changes in one folder. Torchlight holds one per indexed folder.
Overflow
inotify dropped change notices because too many arrived at once. Torchlight answers with a full check.
Fallback
The mode where changes can't be watched reliably, so a full check runs every 30 seconds. Status calls it degraded coverage.
CPU-second
One second of work by one processor core. “0.14% of a core” means 0.0014 CPU-seconds of work every second.
p50, p95, p99
Sort 100 measurements from fast to slow: p50 is the 50th (the typical one), p95 the 95th and p99 the 99th. “p95 is 3.7 ms” means 95 of 100 were that fast or faster.
MB
Megabyte. Memory and disk figures are measured in MiB (1,048,576 bytes) and written as MB, as in the project's other docs.
Steady and peak memory
Steady is what the daemon occupies while nothing happens; peak is the most it reaches, usually during a rebuild.
Frecency
A score that mixes how frequently and how recently you opened something.
Place penalty
A few points a file result loses for where it lives: for being deep below the indexed folder, or inside installed or vendored software. It only reorders matches of similar strength.
Dependency tree
A folder of software installed or copied in by a tool rather than made by you: node_modules, site-packages, vendor, an SDK, a Go module cache.
Excluded folder
A folder named with exclude = in the configuration. Torchlight never reads or watches it, even inside an indexed or allowed folder.
Resolve
Checking a result's id against the current index right before opening it.
